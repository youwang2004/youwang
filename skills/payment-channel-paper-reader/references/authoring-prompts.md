# 分任务精读提示词

全文任务按内容调用对应段落；单独读算法、图表或做汇报时可直接使用其中一段。方括号内填本篇实际对象。每段提示词都要求产出读者能直接读的图、公式或正文。

## 引言、摘要和配套讲稿

> 完整翻译摘要和引言，保留作者比较的对象、转折和限定语。先说清[实际用户]为什么要频繁结算，基础链上的哪个代价让人想到链下。按引言真实顺序，把作者从上一类方案转向下一类的理由嵌回译文旁。另写可以独立阅读的《前因后果》：普通场景怎样工作，只改变哪个条件，谁因此在第几步卡住或泄露了什么，本文改变了哪里，满足什么假设后付款才能继续？尽量让同一组人物和箭头回答这些问题。若专门要“只写问题”，图画到最后一个后果就收住。

> 结合模型、相关工作和实现，确定[通道、枢纽或网络]属于哪一类。逐一回答谁与谁开通道、维护几份独立状态、谁实际转发、谁只协调。把链类型、结算资产、手续费单位、原型和实测环境分开。跨链时顺着两条链上的两段状态说清如何关联、何时完成或退款。未指定底层链／币种的位置写明缺口。如给一种可能用法，注明是假定的部署情景及它需要的技术条件。

> 把相关工作浓缩为有区分度的对比表。行优先是引言及相关工作中的方案家族，列只取与本文动机直接相关的能力，写清“可以做到，但须满足什么条件”。把本文放在同样口径下。原表有更细结果时，就近嵌入并指出应读哪行哪列。

## 章内公式与算法

> 进入[章名]，先在本章正文前分别列出本章参数、本章实际用到的原式与算法调用。给独立原式原编号或就地呈式，重复调用回指本章入口。写作“算法名(原输入) → 具体输出”，说明每个量属于谁、怎样获得、下游给谁使用。随后分情况：简单算法读输入输出与分支；借用原语写本文实际利用的性质和一次应用；新构造先放原算法的清晰局部、转排原式，再指出相对常规构造改了哪个步骤；交互型伪代码将行号归给相应的人。保留全文符号表，在最终 MD 的真实句子前放 🟥 **关键条件** 或 🟦 **本文改进**。需要文字着色时可加 HTML，检查移除样式后仍保留粗体、方块和原句。

> 展开[验证算法]。在验证人的位置列出已经持有和本轮刚收到的量，还原原文的判断式。把生成端的实际表达式逐项代回去，写出有作用的中间等式、相消条件或谓词结果，直到解释“为何接受、接受后谁能使用何物”。若双方独立生成了参数，分别展示两组推导和跨方传输，严守可见性。失败即停、回退、旧状态保留还是触发争议，按作者写出的分支区分。原文只调用黑盒时核到接口和断点。短式用一行，正常字号下放不下才按语义换行。

### Markdown 中的重点长什么样

以下是按条件写的示例。实际精读时，换成本篇核实的条件和改进，分别贴在相关的验证式、机制或比较表旁。

> 🟥 **关键条件**　若本轮更新要求付款人和收款人分别签署自己的记录，缺少任一份授权，这笔付款就无法被采纳。

> 🟦 **本文改进**　若基线要求所有成员签署每次更新，而本文允许其余成员沿用旧授权，就应指出这笔付款少等了哪些成员，以及谁仍需签署什么。

两份 Markdown 都是可编辑的源稿。把方块和加粗标签直接写在实际段落中，数学维持原排版。关键条件也可以是决定结论的假设、验收门槛或失败后果。只有能指明相对基线改了哪一步时才标为“本文改进”。需要字体颜色时可对短语另加 HTML。仅支持基础 Markdown 的阅读器仍能显示两段的含义。每处高亮应回答一个具体问题，重复出现的术语维持常规字重。

## 按材料画交互与完整实例

> 先看原模型和原交互框，再决定哪一种画法能让读者沿箭头重放。[三方枢纽]优先尝试 Accio 式直接三列；长构造可像 BlindHub 一样拆成付款端与枢纽、枢纽与收款端两组，按协议真实先后接回同一次支付。[图中是伪代码]先像读 XPCH 那样从行中找实体、发送、验收、返回，辨认本地计算与跨方消息。[支付网络]逐跳画实际经过的边，请求与回传分别标注。[抽象服务或非典型支付]用实体下的动作框和带语义的箭头表示触发与输出。材料不适配已有样式时先按自己的理解给出可核验成图，并在交付说明新模式。

> 对模型只写任意两方的多方通道，先说清原文的抽象角色，再在安全阈值允许时用三至四人实例化。原文给金额符号就沿用，必须区分多笔时只加已说明的示例索引。给出了具体数值就验算。按事件先后分面，横排或换行均可。同一个模型支持成员变更时，可以让第一次由甲向乙支付，乙退出后丁加入，下一次由丙向丁支付，直至关闭。每一面画出实际发送者、接收者、必要记录字段、核对与生效状态，区分退出者的历史证据和当前成员表。若论文只定义固定成员，例子保持固定成员。

> 在《前因后果》用一笔完整实例串起准备、支付、状态确认和收尾。总图沿用作者模型的图标、通道边界和线型，信息密集就下面逐阶段放大。图内只放短动作、必要实参和验证条件。相关本地计算用整篇统一的实线框或虚线框圈出，让读者能跟着算；用 Abort if、Verify、Return 等与原文相符的短词。原章保留自己的原图与局部推导。检验某人是否需要签字时，圈出本笔的授权者、协调者、核对者和仲裁者；有共识协议才标其投票、证书与提交点。

> 把故障从最后一个正常共同状态分出去。逐个判断：是付款当事人拒签、旁观者不配合、协调者违规，还是链上出现旧状态／不实举报？只挑本篇定义的情形。各图复用正常图的角色位置和线条，把出问题的动作标出来。用一行说明哪笔付款能继续、谁留哪份可验证的证据、何时有退出或处罚分支。分清诚实运营者下的活性与运营者作恶时的余额安全。

## 原图、实验和安全内容

> 每张原图、原表放到被解释的段落。先读原图，再写图下注解；关键参数流、验证条件或状态出口容易看错时，在文字解读旁放同源的标注图，用短箭头、方框点出一项必要条件、验证目标或状态出口。长理想功能或算法框按意义分段截，每块下解释触发、动作和输出，再衔接下一块。正文用合适栏宽，无损原图可放大。生成或标注后在最终大小检视下标、线宽、端点和图例。实验章节逐段完整翻译，直接放原图表，短释比较对象、坐标单位和实际趋势。

> 针对[安全主张]，保留对手可腐化谁、能看到什么、能拖延或拒绝哪个动作、哪些保证需要额外前提。环境和模拟器的额外说明控制在理解这一条证明所需的范围。把支付协议真实执行的验证同安全定义里的理想检查分开，读者能指出作者证明了什么、在哪些假设下成立。

## 收尾和下次复用

> 原结论先译，再用自己的话写清最重要的问题和机制贡献。将参考文献按期刊、会议及其他资料分开，按真实年份从新到旧，同年按核实的 CCF 等级，并附由同一书目生成的档次索引供从 A 到 C 查找。中文专业译题为主，保留英文原题及场所，A 类会议写明会名；系统或算法名称旁说明其含义。逐条过一遍本机所有已读论文，成稿只留下有证据可比的。提出“把甲的机制接入乙”时写明接口、原假设是否仍成立、会改变哪些状态、最小验证该怎么做。

> 交付两份成稿链接后再更新本机“已读论文”。按 DOI 或题名核对是否重读，把本次核实的总结、思考、更正及一至两张代表原图合入同一条。候选新画法可以在本次交付中提示，待用户验证是否适合复用。

## 从实际成稿回查

拿出两份已经保存的 MD，实际打开对应段落做以下检查。某项对本篇适用却没有落点，就在那一段修好；确实没有该类材料时如实交代。局部任务只查所问范围。

| 读者操作 | 应当在成稿中看到什么 |
|---|---|
| 只打开精读的摘要、引言、任意技术章 | 摘要与引言有完整译文，解释和图贴在相应转折。技术章从自己的参数、公式与接口进入，不必到篇末找定义。 |
| 只打开《前因后果》 | 从具体使用场景、部署依据和基线出发，经过问题与贡献，能沿实例走到结算或论文定义的终点。只指定问题的面板在后果处结束。 |
| 遮住算法解释，顺着关键图的一条箭头 | 发送人框内能查生成式，箭头能查实际载荷，收件人框内能查验收与结果；用发送人的本轮输出能解释接收人的检查。按原文能推而未印出的中间步骤实际写出来。 |
| 把浏览器或阅读器的颜色样式去掉 | 两份 MD 中的真正关键条件与机制改动仍能靠方块、粗体、文字标签识别。数学式仍可读。 |
| 读核心原图、理想功能或实验 | 关键图有同源的框箭标注和紧邻的短释；长理想功能按分支拆短；实验保留完整译文、原表原图及简短图解。 |
| 分别检查两份成稿的正文和篇末书目 | 阅读摘要、引言直至结论、附录及图表说明，确认文献方括号、连号和上标只出现在参考文献中。读一遍原来由编号代指作者或方案的句子，确认对象明确。按语义保留数学区间、索引和公式编号。 |
| 在书目里查一篇早年的 A 会和一篇最新论文 | 从档次索引和年份主表都能定位相应条目，原编号、中英文题名、会刊、年份和等级齐备。已读库代表图能帮助下一次选择真实画法。 |
