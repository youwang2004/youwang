## 1. 通道类型、角色与实例

先从模型、协议正文和算法核对参与者、通道实例与状态归属。把以下类别作为可扩展的识别表，而不是论文必须覆盖的章节；同一论文可以符合多个维度。

| 论文中的实际结构 | 核对的角色与通道 | 流程图应突出什么 |
|---|---|---|
| 双方直接支付通道 | 两名通道成员，共同管理一条通道 | 两方各自的计算、签名交换、状态更新与退出条件 |
| Hub／Tumbler 等三角色支付 | 发送方、中介、接收方；通常涉及两条双方通道，但必须依本文核实 | 各条通道的独立状态，以及承诺、秘密、签名在两边如何绑定和流转 |
| 三方或更多成员的共享通道 | 同一通道中的实际成员集合；付款双方与其余成员的职责可能不同 | 谁提出支付、谁验证或参与状态维护、哪些状态由全体共享 |
| 多跳支付通道网络 | 发送方、实际中间节点、接收方，以及沿途多条通道 | 路径顺序、跨通道条件与原子性依赖、超时和退款方向 |
| 虚拟通道、通道工厂或分层结构 | 基础通道与上层通道各自的成员、辅助者与资金依赖 | 开通／关闭时的协助与正常更新时的参与范围，区分不同层的通道状态 |
| 其他或混合模型 | 按论文补充角色、通道关系、状态维护方式与信任假设 | 画出实际关系，不硬塞进已有类别 |

- **分开记录人数与结构。** 三名角色不等于三方共享通道；经过中介的两条双方通道不等于一条三方通道。通道成员数、付款人数、付款笔数和验证者数分别核对。
- 论文是两方就画两方，是三方就画三方；链、合约、协调者或观察者仅在相应阶段实际参与时加入，身份单列，不计作额外付款人。不为了匹配参考图补造第三方、委员会或区块链消息。
- 保留原文角色名、符号和通道标识。论文允许且有助于看清各方职责时，主动选择满足成员数、阈值和网络假设的小实例。原文已有小规模例子但未逐人展开时，沿用其参与方，补全本文实际定义的发送者、接收者和本地动作；用图外一句说明实例条件。不同论文按实际结构决定人数。
- 明确每个角色已知和隐藏的对象。示意图中的信息流不能让中介、其他成员或观察者突然获得协议未公开的付款关系、金额或秘密。

## 2. 支付情况与分支

先形成“共同前置阶段 → 不同执行情况 → 各自输出状态 → 可复用后续阶段”的结构。按实际论文与用户问题选择下表中的情况，不能只画一名付款人的一次成功就宣称覆盖完整场景，也不要把所有行都硬加进只支持单笔更新的论文。

| 分类维度 | 可区分的情况 | 必须核对的差异 |
|---|---|---|
| 方向与通道能力 | 单向、反向、双向更新 | 资金来源、角色职责与签名／状态构造是否改变；单向协议不能自行画出反向支付 |
| 请求数量与参与关系 | 单笔；同一人多笔；两名或更多付款人；同一收款人；互不重叠的支付对 | 逐笔列发送／接收方、消息、余额输入与结果，不混淆“人数增加”和“笔数增加” |
| 执行关系 | 串行、允许并发、批处理、跨批次流水线 | 谁能并行提出、何时排序、是否在同一批、何时形成和提交一致状态 |
| 竞争与冲突 | 同一余额被重复使用、旧状态、签名或证明无效 | 原文如何检测、排序、拒绝、延后或恢复；没有定义的机制不能凭空补齐 |
| 正常与异常结果 | 成功、拒绝、无响应、离线、超时、退款、争议、惩罚 | 触发点、最后共同状态、超时条件、资金去向与能否继续更新 |

- 用户问“两个人同时支付”时，先核对原文是否允许并发，再按该论文构造代表性情况。可以先画两组不重叠支付；存在共享付款人、收款人或通道时，另核对余额、状态与冲突处理，不能直接复制独立支付的结论。
- 多笔支付保留原文符号与每笔调用的作用域；可用角色标题、分面和文字说明区分，不能私自添加上下标或改名。不要为了排版默认两笔金额相等、两笔都成功或必在同一批提交；这些示例条件需由论文或本次明确选择支持。
- 允许并行提出不等于允许独立提交；流水线重叠也不等于同一批中所有操作同时发生。图中分别表示请求、本地生成、排序、验证、投票、候选状态与最终状态。
- 原文未支持某情况时，保留实际支持的流程，并简短说明所问分支缺少什么定义；不要把猜测画成协议。证据分类在工作底稿或图外处理，不在每个图块重复塞“原文是否说明”的制作注释。
- 创建或资金准备相同时只画一次，再从更新阶段分出单笔／多笔等情况；后续关闭条件相同时可以汇合复用，但须承接各分支实际得到的最终状态。不同通道、签名条件、资金状态或退出方式不能只因外观相似而合并。
- 拒绝、退款和惩罚从其实际触发点分出；不能接在正常成功后，误画成每笔支付都必须经过的步骤。分支条件和出口应清楚，复杂分支拆成相邻面板并保留前后状态。

## 3. 图形布局选择

先决定读者需要看清的是交互时序、局部协议算法、协议分支、结构关系还是交易依赖，再结合实际消息数、标签长度、并发关系、原图风格和交付空间选布局。两方、三方、四方都可以画清楚的直接交互图，不能仅凭人数判定箭头会乱，或把用户对一处坏走线的批评变成所有图的禁令。用户给出的不同样式是可按需采用的表达方式，不要求一次全部生成，也不固定为以下有限几种。

| 主要表达目标 | 优先考虑的布局 | 布局约束 |
|---|---|---|
| 两方、三方、四方等角色间的消息交换，直接连线可读 | 参与方置顶分列、本地计算与验证归所属方、用直接箭头连接消息 | 可带细生命线，也可用留白分列；箭头保留字段，真实因果清楚，不因人数机械改用卡片 |
| 注册、谜题承诺、签名交换等紧凑局部交互协议 | 双栏／多栏论文式协议框：列首角色与输入、列内伪代码、列间带消息的箭头 | 保留检查、abort／return、输出与跨方传递；不强拉生命线，也不拆散成各方独立算法而丢交互 |
| 完整生命周期与多种付款情况 | 公共阶段＋分支面板＋满足条件时的汇合 | 例如公共创建 → 单笔／并发更新 → 各自状态承接共识或关闭；不照搬这套阶段名称 |
| Hub、跨通道或多层结构 | 按通道／层分组的交互面板，必要时用嵌入的局部时序图 | 同一角色可以跨组，但通道、资金和状态不得混同 |
| 输入输出的花费条件、正常与惩罚路径 | 交易依赖图或分支图 | 标出被花费输出、签名／秘密／时锁条件；依赖箭头不当作消息发送 |
| 多方验证、广播、批次与流水线 | 分阶段共识面板、必要的时间轴与明确的广播表示 | 保留发送者、接收集合、消息、批次、阈值与提交点；不凭空引入集中收集者 |
| 结构和执行两者都复杂 | 简洁总览＋局部详细时序图 | 总览负责分类与衔接，细图负责真实算法、消息与时序，不只给概念示意 |

- 时序布局的具体排版遵循 [论文式交互图](figure-walkthrough.md#论文式交互图的转排)；紧凑协议框、分支／架构布局不强制拉满生命线。全景阶段图可以嵌入少量必要的直接箭头；多种布局可服务同一论文的不同层次。
- 清楚的直接消息箭头与广播扇出正常保留。只有实际拥挤或含义不清时，才通过调整行距、标签位置、连线高度、分区或局部面板修复；密集广播可选逻辑摘要并注明发送者、原消息字段与接收集合，不能把一切交互替换成“发送者→集合”的文本卡片。逻辑摘要不是中继或实体总线，不隐藏不同内容、轮次、接收范围或原文没有的传播条件。
- 将消息箭头、阶段连接、交易依赖和状态转移通过标签或明确分区区分。少量低饱和分区色、细线、统一数学字体和留白即可；不堆装饰性网络、人物连线或无信息箭头。
- 内容过多时拆图，保持角色顺序、阶段／动作名称、原符号和前后状态连续；不通过无限加宽、拉长或缩小字号塞进一张不可读大图。

### 按原图覆盖情况补图

先读原图、图注、协议正文及相应附录，按阶段对照角色、消息、检查与输出，补足会妨碍重放的缺口。常见情况可组合处理：

| 原文已有材料 | 补图处理 |
|---|---|
| 只有更新交互图 | 沿用清楚的更新原图，按正文／附录补出实际定义的创建、关闭或关键异常交互。以原图的角色顺序和线型为参照，状态及授权条件从原文各阶段承接。 |
| 只有抽象系统模型图 | 保留模型图定位角色和信任边界，另画关键执行阶段。按协议分解具体谁计算、传给谁、接收方如何处理及何时更新状态。 |
| 两条通道分别写成算法，散在正文或附录 | 若属于同一笔支付，合成一张三方交互图。中介使用同一角色列，两侧按原文区分各自通道和状态，标出跨边传递的对象、前置条件和完成点。例如原文使用 S、T、R 时，显出 S–T 与 T–R 的因果衔接。图太密时使用连续面板，仍保留三方视野。 |
| 原图已清楚画出交互 | 直接展示并沿图解释；缺失的关键分支、检查、跨轮连接或状态用相邻局部图补充。覆盖完整时复用原图。 |

同一组图先确定参与方顺序、阶段方向、数学字体、箭头／线型语义、颜色和留白，各阶段沿用。不同内容需要结构对比图、交易依赖图、分支图或状态机时仍可换布局，保留通用视觉约定。材料不足时只画有依据的关系，图外说明缺口。

## 4. 算法和消息如何入图

- 图必须让人跟随“谁计算 → 谁发给谁 → 对方检查什么 → 得到什么新状态”。在对应角色或步骤旁写实际算法调用、已知输入、关键计算与校验式；不能只放角色图标、“生成签名”“执行共识”等笼统标签。
- 区分原语内部算法和协议层调用：交互图保留本步所需的完整已知调用、实际参数、关键结果与必要校验；原语内部完整循环和推导需要时另作算法框，不把所有底层细节塞满流程图。算法框仍遵循 algorithms-playbook.md 的已定义输出和原文顺序，直接正常显示公式／伪代码，仅保留原伪代码已有的行号，不附加源码。
- 图中调用与参数沿用原文，包括横线、帽号、字体、大小写及参数顺序；原文只给缩写接口时不悄悄补输入。每个签名、证明、承诺与秘密应能追踪到生成者和使用者；多通道／多笔时不能把不同会话误当作同一个对象。
- 图中中文使用简短动作和条件，解释和推导放在图旁正文。箭头附近保留完整已知消息字段；长字段分行，必要时用紧邻的消息框与该箭头一一对应。计算、广播、接收验证和最终提交分别表示。区分链下交换与链上发布／确认。
- 标明每种情况的已有输入和输出状态。全文讲解需要时在图外补符号解释及失败去向；单独要图时，直接给干净可读的成图，不强行附上整篇报告、长注释或重复算法截图。会改变理解的限制须简短说明，不能为整洁省去必要条件。

### 总览与关键阶段详图

总览用于定位角色和阶段；关键阶段的局部图须让人读到执行方的实际调用／计算、完整已知消息字段、接收检查与阶段出口。必要时拆成连续面板，保持角色、记号和参数接续；底层算法的重复展开可留在紧邻正文，不能以“生成签名”“验证证明”“更新状态”等标签取代全部细节。

图的数量由实际阶段、分支和可读性决定。多阶段有不同秘密或状态依赖时，按需提供足够详图；不为少画图省略必要交互，也不为达到固定图数画无关样式。图下连续解释对象来源、必要先后和输出用途，不能只放图注。

### 图内数学排版

生成图统一采用正式论文的数学排版，适用于参与方名称、消息字段、算法／函数调用、局部计算与箭头标签，不能只规范图外正文。

- **数学对象真实排版。** 使用 LaTeX／TikZ 或等效数学排版生成清晰文字／矢量字形后成图。不得用普通文本、Unicode 上下标、组合帽号／横线或手工挪位近似公式；SVG 容器也须嵌入正式排版的数学内容。
- **记号与正文一致。** 保留原文的大小写、字体、粗体、花体、上下标、帽号、波浪号、横线和撇号及其覆盖范围。例如角色写成 \(P_s,M_s,P_h\)，向量预签名按原文完整显示 \(\widehat{\boldsymbol{\sigma}}_{M_s}^{2}\)，不能把修饰挪位、丢掉或改成近似文本。
- **字体有语义。** 采用统一的论文式数学字体；变量通常用数学斜体，算法／函数名及多字符标识通常用正体，向量、集合和其他特殊字体以原文定义为准，不一律加粗或改成普通字母。解释性中文与数学对象分开排版。
- **标签清楚。** 数学字号、基线、上下标比例、线宽及留白统一；长标注按语义换行或调整局部布局，不能挤压符号、缩小到难读或把参数改成不完整简称。
- **按最终成图核对。** 除语义、方向和端点外，实际查看图内字体、修饰覆盖范围及上下标归属；发现纯文本近似或符号缺失时修正受影响标注再交付。只维护规则时不为演示规范额外制图。

### 两类协议图

- **原文章节的直传参数图。** 放在原文实际介绍交互的节、段或分步流程旁，依原文顺序展示参与方及参数的直接传递，箭头标明方向与实际载荷。作者用文字给出完整流程时也据此成图。若原图已清楚表示这些信息，可直接用原图。需重建或补画时，与本节的完整译文和独立讲解相邻。
- **篇末完整交易流程章的论文式分列图。** 参与方各占一列，本地计算、具体调用和逐步推导写在对应列，实际传递的消息与字段写在列间箭头上。图内按顺序展开已知参数的代入、计算、检查、分支、状态更新和输出。共享阶段与不同执行线按原文关系衔接，每个面板交代承接参数。优先使用 LaTeX／TikZ 或等效数学排版，采用黑字、白底和细线。图内主要是公式、伪代码和符号，短英文连接词可用 Let、If、Abort if、Else、Send、Return。关键子程序、调用前置条件或必须通过的检查可用细实线或虚线框突出。详细中文解释和原文疑点放图后。过长时在阶段、参与方或消息交接处拆分，并给出继续点与变量映射。
- **两类图分别回答不同问题。** 原章节的图帮助读者定位谁把什么发给谁，篇末图帮助按序重放一笔付款并核对每个量怎样算出。仅明确其作用的原文接口可据实排入图中。能够从已给定义推出的式子展示代入依据，材料缺失处标明边界。

### 独立章的步骤标注与版式

- **标号贴着动作。** 仅在「完整交易流程」章的执行面板使用章内序号，例如 ① 发请求、② 接收检查，或在同一检查框内用 (a)、(b)、(c) 标各判定条件。编号放在对应执行方的动作框左侧或消息箭头附近，跨图用同一阶段名和连续的局部编号衔接。原文编号照录，不把整理步骤号当作算法号、公式号、参与者 ID 或轮次。并发动作可并列或共用一组编号；逻辑条件列表不暗示额外执行顺序。
- **按实际列宽排公式。** 先把计算、判定和输出对齐实际执行者的列或明确归属的协议框，消息元组放在对应箭头旁。能以正常字号在一行完整显示的调用、赋值和元组保留一行。确实过长时优先调整栏宽或分面，再按逗号、等号或完整运算项换行，续行对齐。保留全部参数与语义，不缩字硬塞，也不把短式机械分行。
- **黑白论文排版。** 新制图统一黑字白底，靠线型、位置、数学字体和少量短词区分角色、失败条件和分支。用可追踪的入口和出口连接各张图，版式依真实交互调整。原图对照保留源图，明确要求黑白展示时标明另制的黑白副本。

## 5. LaTeX 制图与交付验收

1. 先完成类型识别、场景划分和依赖检查，再用可编译的 LaTeX／TikZ 等精确排版生成论文式图。公式和箭头必须真实渲染；不把 LaTeX 代码、数学数组或箭头字符清单冒充成图，不用生成式位图猜画精确公式与协议箭头。
2. 先核对角色、通道数、支付方向、各分支的实际算法和状态衔接；再核对并发范围、冲突处理、广播接收范围与最终生效点。
3. 实际渲染并检查图内文字、数学、端点和留白。固定坐标布局尤其检查计算框、消息标签、阶段横框、页边是否相交；按渲染后的字宽、行高和容器边界安排位置。发现任何信息被背景、文字或线遮挡，先移位、留白、换行或拆图，再渲染、打开复验。按 [成图可查看性验收](figure-walkthrough.md#成图可查看性验收) 检查正文宽度和点开原尺寸两个视图。
4. 在聊天回复中直接嵌入已核验的清晰图片；论文精读时紧邻解释图的对象、箭头、关键步骤及前后衔接，整合文档中同步嵌入。单独要图时以图片为主要交付。不默认附 PDF、压缩包或源码，也不只给图片链接；用户明确要求相应格式时再提供。编译过程可有中间 PDF，它不属于默认交付物。
5. 图中只保留理解流程必要的角色、阶段、算法、消息、分支条件和状态。在内部核对来源，必要解释放图外；用户只要图时以图为结果。生成失败则如实说明未完成项，不宣称已经可查看。

## 6. 持续补充分类

后续出现新的通道类型、付款关系或用户认可的表达方式时，先判定应补到类型、情况、布局还是验收部分，再合并相应规则。优先复用现有分类并保留其他对话已加入的有效要求，不按论文名堆积互相重复的专用模板；每次保存按 evolution.md 和 distribution.md 的最新版合并与同步流程执行。

## 背景辅助图与论文风格

引言或预备知识中有难以凭文字看清的关系时，先看论文相关原图及图注，借鉴专业论文的角色分组、线型、数学字体和留白，再选最简单的布局。按需要补结构对比、问题演进、冲突／异常场景或基础机制图，例如多方排序和共识阈值。以原文和已核实知识确定图义，区分通用机制与论文实际采用的构造。

每张图集中讲清一个关系，例如旧方案的限制怎样引出本文问题。沿用原文角色和结构，金额等数值仅在确需直觉且符合模型时补充。用描述内容的自然标题，例子的适用条件在邻近文字或图注交代，原图出处留作内部核对。正常字号、少量颜色、短标签及一致图例便于阅读；用户样稿的装饰、页码和标注颜色随实际场景取舍。

## 箭头清晰度与按需修复

先核对发送者、接收者／接收集合、消息字段、接收检查和因果，再选几何表达；不为少画线改变通信路径、消息可见性或实际协议。

- **正常连线优先保留。** 两方、三方、四方等只要图清楚，就用参与方列与直接箭头，跨过未参与的中间生命线也是允许的，不自动表示向中间方发送。广播可以清楚扇出或使用有明确分支与收端标记的多接收连线；多接收不等于含混。
- **只修实际问题。** 真正要处理的是无法辨认发送／接收端、消息对应不明、标签压线、多个发送者路径混淆、线穿公式或严重重叠。先移动标签、增加必要留白、调整高度与走线；能局部修好就不整图换模板。允许清楚的长箭头、折线或交叉，不为追求零交叉改坏语义。
- **多方广播按需组织。** 不同发送者可以错开消息行、划分区域或拆局部面板；仅当逐线展示确实密集、且摘要不会损失需要讲清的接收与校验关系时，才用广播消息框／接收集合摘要。摘要必须保留原文真实字段，不能只留下“UPDATE”等泛化标签，也不能把实际消息替换成无内容的大卡片。
- **先后与并发分开。** 纵向错位、左右排布或阶段分面可能只是排版；原文允许并发时明确同组并发，不因图上位置捏造全局顺序、协调者、聚合点或新条件。
- **短标签与完整信息兼顾。** 长消息字段可在箭头旁分行，或用紧邻的消息框与清楚连线对应；计算和检查留在执行方。按实际文本边界留空间，保留箭头头部与横线、帽号、上下标，不缩字遮掩拥挤。
- **验收实际图。** 核对消息、方向、执行方与因果，再看正常缩放下是否清楚；只有发现可见缺陷才定向重排并复核，不循环生成无关风格样图。

## 按需生成与控制重复工作

多样性指按实际论文选择合适表达，不是每次产出多套候选。用户没有要求比选时，先确定一套合适布局再制作；复杂论文可用总览加必要局部图，但不按人数、风格或所有潜在分支穷举出图。

优先复用已经可读且语义正确的图、已确认样式和可编辑源码。总览可合并公共创建与结算阶段。完整交易流程章仍须交代各条独立执行线实际发生的调用、输入输出和状态承接。按实际需要定向修改受反馈影响的图。只改技能规则时做规则与引用检查即可，不额外生成论文成图、批量预览或安装新制图工具。实际交付新图时仍须渲染和目视检查。
