# 支付协议的流程分类与成图

生成或重绘完整支付流程、交互图、分支图、交易图及并发示意时使用。先识别论文实际模型和执行情况，再选图形布局；不要把某篇论文的四人例子或某张样图固化为所有论文的模板。

## 1. 通道类型、角色与实例

先从模型、协议正文和算法核对参与者、通道实例与状态归属。把以下类别作为可扩展的识别表，而不是论文必须覆盖的章节；同一论文可以符合多个维度。

| 论文中的实际结构 | 核对的角色与通道 | 流程图应突出什么 |
|---|---|---|
| 双方直接支付通道 | 两名通道成员，共同管理一条通道 | 两方各自的计算、签名交换、状态更新与退出条件 |
| Hub／Tumbler 等三角色支付 | 发送方、中介、接收方；通常涉及两条双方通道，但必须依本文核实 | 各条通道的独立状态，以及承诺、秘密、签名在两边如何绑定和流转 |
| 三方或更多成员的共享通道 | 同一通道中的实际成员集合；付款双方与其余成员的职责可能不同 | 谁提出支付、谁验证或参与状态维护、哪些状态由全体共享 |
| 多跳支付通道网络 | 发送方、实际中间节点、接收方，以及沿途多条通道 | 路径顺序、跨通道条件与原子性依赖、超时和退款方向 |
| 虚拟通道、通道工厂或分层结构 | 基础通道与上层通道各自的成员、辅助者与资金依赖 | 开通／关闭时的协助与正常更新时的参与范围，区分不同层的通道状态 |
| 其他或混合模型 | 按论文补充角色、通道关系、状态维护方式与信任假设 | 画出实际关系，不硬塞进已有类别 |

- **分开记录人数与结构。** 三名角色不等于三方共享通道；经过中介的两条双方通道不等于一条三方通道。通道成员数、付款人数、付款笔数和验证者数分别核对。
- 论文是两方就画两方，是三方就画三方；链、合约、协调者或观察者仅在相应阶段实际参与时加入，身份单列，不计作额外付款人。不为了匹配参考图补造第三方、委员会或区块链消息。
- 保留原文角色名、符号和通道标识。用户要求用若干人举例时，遵守论文的成员数、阈值及网络模型条件；不能把不适用的协议缩成任意人数。
- 明确每个角色已知和隐藏的对象。示意图中的信息流不能让中介、其他成员或观察者突然获得协议未公开的付款关系、金额或秘密。

## 2. 支付情况与分支

先形成“共同前置阶段 → 不同执行情况 → 各自输出状态 → 可复用后续阶段”的结构。按实际论文与用户问题选择下表中的情况，不能只画一名付款人的一次成功就宣称覆盖完整场景，也不要把所有行都硬加进只支持单笔更新的论文。

| 分类维度 | 可区分的情况 | 必须核对的差异 |
|---|---|---|
| 方向与通道能力 | 单向、反向、双向更新 | 资金来源、角色职责与签名／状态构造是否改变；单向协议不能自行画出反向支付 |
| 请求数量与参与关系 | 单笔；同一人多笔；两名或更多付款人；同一收款人；互不重叠的支付对 | 逐笔列发送／接收方、消息、余额输入与结果，不混淆“人数增加”和“笔数增加” |
| 执行关系 | 串行、允许并发、批处理、跨批次流水线 | 谁能并行提出、何时排序、是否在同一批、何时形成和提交一致状态 |
| 竞争与冲突 | 同一余额被重复使用、旧状态、签名或证明无效 | 原文如何检测、排序、拒绝、延后或恢复；没有定义的机制不能凭空补齐 |
| 正常与异常结果 | 成功、拒绝、无响应、离线、超时、退款、争议、惩罚 | 触发点、最后共同状态、超时条件、资金去向与能否继续更新 |

- 用户问“两个人同时支付”时，先核对原文是否允许并发，再按该论文构造代表性情况。可以先画两组不重叠支付；存在共享付款人、收款人或通道时，另核对余额、状态与冲突处理，不能直接复制独立支付的结论。
- 多笔支付保留原文符号与每笔调用的作用域；可用角色标题、分面和文字说明区分，不能私自添加上下标或改名。不要为了排版默认两笔金额相等、两笔都成功或必在同一批提交；这些示例条件需由论文或本次明确选择支持。
- 允许并行提出不等于允许独立提交；流水线重叠也不等于同一批中所有操作同时发生。图中分别表示请求、本地生成、排序、验证、投票、候选状态与最终状态。
- 原文未支持某情况时，保留实际支持的流程，并简短说明所问分支缺少什么定义；不要把猜测画成协议。证据分类在工作底稿或图外处理，不在每个图块重复塞“原文是否说明”的制作注释。
- 创建或资金准备相同时只画一次，再从更新阶段分出单笔／多笔等情况；后续关闭条件相同时可以汇合复用，但须承接各分支实际得到的最终状态。不同通道、签名条件、资金状态或退出方式不能只因外观相似而合并。
- 拒绝、退款和惩罚从其实际触发点分出；不能接在正常成功后，误画成每笔支付都必须经过的步骤。分支条件和出口应清楚，复杂分支拆成相邻面板并保留前后状态。

## 3. 图形布局选择

先决定读者需要看清的是交互时序、协议分支、结构关系还是交易依赖，再自主选择布局。用户给出的样图用于风格与信息组织，不强制所有论文采用同一种几何结构。

| 主要表达目标 | 优先考虑的布局 | 布局约束 |
|---|---|---|
| 少量角色间有严格先后依赖的消息交换 | 参与方置顶、固定列和生命线、时间向下的论文式时序图 | 本地计算归入执行方，箭头连接真实发送与接收方 |
| 完整生命周期与多种付款情况 | 公共阶段＋分支面板＋满足条件时的汇合 | 例如公共创建 → 单笔／并发更新 → 各自状态承接共识或关闭；不照搬这套阶段名称 |
| Hub、跨通道或多层结构 | 按通道／层分组的交互面板，必要时用嵌入的局部时序图 | 同一角色可以跨组，但通道、资金和状态不得混同 |
| 输入输出的花费条件、正常与惩罚路径 | 交易依赖图或分支图 | 标出被花费输出、签名／秘密／时锁条件；依赖箭头不当作消息发送 |
| 多方验证、广播、批次与流水线 | 分阶段共识面板、必要的时间轴与明确的广播表示 | 保留发送者、接收集合、消息、批次、阈值与提交点；不凭空引入集中收集者 |
| 结构和执行两者都复杂 | 简洁总览＋局部详细时序图 | 总览负责分类与衔接，细图负责真实算法、消息与时序，不只给概念示意 |

- 时序布局的具体排版遵循 [论文式交互图](figure-walkthrough.md#论文式交互图的转排)；分支／架构布局不强制把所有角色挤到最上方或拉满生命线。
- 优先用对齐分区、并排分支和短的正交连线减少交叉。同类广播可用独立的逻辑广播符号并注明发送者、消息与接收集合，不必逐条画满点对点箭头；逻辑符号不是中继或实体总线。不隐藏不同内容、不同轮次或不同接收范围，不暗示论文没有的转发、集中聚合或消息可见性。不同发送者分开消息带，禁止同一路径穿过多方并放置多枚无归属箭头。
- 将消息箭头、阶段连接、交易依赖和状态转移通过标签或明确分区区分。少量低饱和分区色、细线、统一数学字体和留白即可；不堆装饰性网络、人物连线或无信息箭头。
- 内容过多时拆图，保持角色顺序、阶段／动作名称、原符号和前后状态连续；不通过无限加宽、拉长或缩小字号塞进一张不可读大图。

## 4. 算法和消息如何入图

- 图必须让人跟随“谁计算 → 谁发给谁 → 对方检查什么 → 得到什么新状态”。在对应角色或步骤旁写实际算法调用、已知输入、关键计算与校验式；不能只放角色图标、“生成签名”“执行共识”等笼统标签。
- 区分原语内部算法和协议层调用：交互图保留本步所需的完整已知调用、实际参数、关键结果与必要校验；原语内部完整循环和推导需要时另作算法框，不把所有底层细节塞满流程图。算法框仍遵循 algorithms-playbook.md 的已定义输出和原文顺序，并按 wps-latex.md 自动选型、不显示公式／行号。
- 图中调用与参数沿用原文，包括横线、帽号、字体、大小写及参数顺序；原文只给缩写接口时不悄悄补输入。每个签名、证明、承诺与秘密应能追踪到生成者和使用者；多通道／多笔时不能把不同会话误当作同一个对象。
- 箭头附近保留完整已知消息字段；长字段分行，必要时放紧邻的消息框。计算、广播、接收验证和最终提交不能画成一步。区分链下交换与链上发布／确认。
- 标明每种情况的已有输入和输出状态。全文讲解需要时在图外补原文定位、符号解释及失败去向；单独要图时，直接给干净可读的成图，不强行附上整篇报告、长注释或重复算法截图。会改变理解的限制须简短说明，不能为整洁省去必要条件。

## 5. LaTeX 制图与交付验收

1. 先完成类型识别、场景划分和依赖检查，再用可编译的 LaTeX／TikZ 等精确排版生成论文式图。公式和箭头必须真实渲染；不把 LaTeX 代码、数学数组或箭头字符清单冒充成图，不用生成式位图猜画精确公式与协议箭头。
2. 先核对角色、通道数、支付方向、各分支的实际算法和状态衔接；再核对并发范围、冲突处理、广播接收范围与最终生效点。
3. 实际编译并打开图片目视检查中文、数学字体、原文符号、箭头端点、字号、间距、重叠、裁切和正常缩放可读性；同时查看缩略总览与必要的局部。发现交叉拥挤、公式越界或字太小就重排或拆分，不能仅凭编译成功交付。
4. 在回复或文档对应位置直接嵌入已核验的清晰图片，默认只交付图片；用户要整合文档时嵌入 `.md`。不默认附 PDF、压缩包或源码，也不只给图片链接；用户明确要求相应格式时再提供。编译过程可有中间 PDF，它不属于默认交付物。
5. 图中只保留理解流程必要的角色、阶段、算法、消息、分支条件和状态。来源核对、制作过程和其他长说明放图外；用户只要图时以图为结果。生成失败则如实说明未完成项，不宣称已经可查看。

## 6. 持续补充分类

后续出现新的通道类型、付款关系或用户认可的表达方式时，先判定应补到类型、情况、布局还是验收部分，再合并相应规则。优先复用现有分类并保留其他对话已加入的有效要求，不按论文名堆积互相重复的专用模板；每次保存按 evolution.md 和 distribution.md 的最新版合并与同步流程执行。

## 背景辅助图与论文风格

引言有具体理解障碍时，先查看论文相关架构／问题图，提取角色分组、线型、字体、配色和留白等视觉语法，再画简洁教学图；不能只凭截图外观推定本文机制。可选结构对比、问题演进、并发冲突、拒绝配合或旧状态问题面板，但仅采用本文实际讨论的场景，不强制凑固定数量。

每张图突出一个背景因果：“需求为什么出现 → 既有方法解决到哪 → 还缺什么 → 本文怎样切入”。沿用原文角色与结构，必要教学情景标注“教学示意”，金额等数值仅在确需直觉且符合模型时补充。默认正常字号、少量颜色、短标签和一致图例，别把用户幻灯片中的装饰人物、页码或红字范围固化成模板。原图与辅助图分别标明，不把教学图写成论文原图。

## 广播、箭头与标签的几何规则

先做不依赖排版的消息清单：发送者、接收集合、消息原字段、产生条件、接收后的本地操作与必要因果。再选几何表达；不能为了少画箭头改变消息可见性或通信路径。

- **一发送者一消息带。** 多方各自广播时，每位发送者占独立纵向区域，先显示本地生成，再显示发送；消息标签固定在本区域，不压到下一发送者的线。原文允许并发时以同组／并发括号说明，纵向错位仅为排版，不新增执行顺序。
- **端点可追踪。** 点对点消息每条线只有一个明确发送端和一个箭头接收端，端点落在对应生命线／节点边界。跨过中间生命线不表示向其发送；尽量通过不同高度或局部面板避免视觉误读，不能在交叉点额外加箭头。
- **广播的两种干净表示。** 少量接收者可以同发送点扇出、收端错开高度，并给共同消息一个不压线的标签；密集全互联时使用单独广播消息卡“发送者 → 明确接收集合：消息”并与该角色区域连接。消息卡是广播的视觉摘要，不是新角色、集中协调者或实际转发路径。若广播卡仍拥挤，拆成发送与接收验证两个面板并保留因果。
- **禁止含混折线。** 不把多个发送者串成一条折线，不用一条近水平线穿过多条生命线再在中途和末端混放箭头，不用折返线同时表示发送、回传和接收校验；不能仅以“已减少交叉”接受用户示例那种长斜线重叠。
- **正交与短连接。** 非时序的框图优先水平／垂直连接，转角明确；时序图的直接消息优先短、近水平的独立箭头，必要折线留在专用走线区。不得穿过公式、人物、状态框或标签。语义确需交叉时使用清晰避让／跨线记号，不把视觉交叉当作事件节点。
- **标签有空间。** 先测定文字和公式占用的边界，再安排线与框；长字段分行放在箭头上方或紧邻消息框，明确对应哪条消息。箭头头部、帽号、横线与边框均应留空，不能裁掉修饰或压缩成无法读的字。
- **语义与外观双验收。** 同时核对每个发送者是否向正确集合发送、每个箭头是否只有一种含义、每个标签是否唯一关联消息，以及缩略总览是否能一眼看出消息分组。局部放大检查符号、交叉、箭头头部、裁切与文本边界；只编译成功不合格。

不预设所有图都用固定四列或相同人数。论文原图本身拥挤时借鉴其视觉风格并改善走线，不能照搬其拥挤；原文通信模型和依赖始终优先于几何模仿。
